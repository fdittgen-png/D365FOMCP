# DMF SoD-Rule-Entity vs Auditor CSV/Excel — Format Comparison & DMF-as-Reference Gaps (2026-07-08 session)

_Reference for the `d365fo-security-analysis` skill. Read on demand._


From an architecture discussion in `<repo-path>` about whether the D365 `SystemSegregationOfDutiesRuleEntity` DMF export could replace the auditor CSV as the live source of truth for SoD rules (Excel demoted to an intermediate format). Applies to any SoD engine that ingests both a hand-authored matrix and a D365 DMF rule export.

### The two source formats are not peers — they operate at different abstraction levels
- CSV/Excel defines conflicts at **task** granularity (business tasks like "Post AP Invoice") via a hand-maintained task→bucket table (`$TaskMapping` in `Update-SodMatrixes.ps1`) and natively carries the PROC/SALES/FIN grouping as CSV sections (P2P/O2C/R2R).
- DMF entity export defines conflicts at raw **AOT duty** granularity (`FIRSTSECURITYDUTYIDENTIFIER`/`SECOND...`) and has **no native matrix/business-cycle concept** — grouping is faked in `SecAnalysisDmfConverter.psm1` by regexing a `P2P -`/`O2C -`/`R2R -` prefix out of the free-text `NAME` field, a convention only `New-SodRulesPackage.ps1` bakes in. A rule authored/edited directly in the D365 UI keeps D365's default name (`"New Segregation of duties rule"`) — no prefix → silently defaults to PROC with only an aggregate `unknownSection` count, no per-rule attribution.
- Both formats converge on the same D1–D46 bucket vocabulary only via **separate, independently hand-maintained mapping tables** (`$TaskMapping` for CSV, `DutyMapping.xml` for DMF) — the two tables must stay conceptually consistent with each other even though nothing enforces that.

### DutyMapping.xml cannot become obsolete by switching rule sources
- It has two independent call sites: (1) `SecAnalysisDmfConverter.psm1` — translates a *rule definition's* AOT duty pair into buckets so it can be expressed as a `<conflict>`; (2) `SoD_merge-Refactored.ps1` (the core engine, `Build-DutyMappingHashtable`) — translates every **real user's live granted AOT duties** (from the D365 security model export) into buckets so those grants can be checked against the matrix at all.
- A DMF rule export only says "duty A conflicts with duty B" — it says nothing about which real users hold duty A or B. That's a wholly separate data source (the live role/duty/privilege export), which speaks the same raw AOT-duty vocabulary and needs the identical mapping table. Retiring DutyMapping.xml would require re-architecting the detection engine and every downstream report (duty matrices, license optimization) off the D-bucket model entirely — a much bigger change than swapping the rule-definition format.

### Concrete gaps if a raw D365 DMF export were fed in directly (not the script-generated ZIP)
- **Transport**: `Publish-SodMatrixes` only accepts a ZIP (PK magic-byte sniff → routes to the DMF converter) or the internal `<sod-matrices>` XML (root-element check). A bare `<Document>` entity export posted directly fails root-element validation — must be zipped first even when hand-crafted.
- **Full-replace, not merge**: a DMF publish clears and replaces *every* `<conflict>` in the target matrix (`SecAnalysisDmfConverter.psm1` ~line 399). Publishing a partial export (e.g. one rule, or rules for only some duty pairs) silently deletes every other conflict in that matrix. A live-sync workflow must submit the *complete* current ruleset per matrix every time, or add merge-by-key logic — neither exists today.
- **No effective-dating / currency filter**: the entity table is a full edit-history (`VALIDFROM`/`VALIDTO`); the same conceptual rule reappears every time it's amended. The converter has no "keep only the current version" step — it processes every historical row. Source/target dedup with "strictest severity wins" happens to converge safely on monotonic severity increases, but silently mis-handles a genuine severity downgrade or a rule later deleted in D365 with no successor row (it would still get "converted" and never expire).
- **RISK/MITIGATION text is discarded.** The internal format's `description` attribute (served to callers as `businessRule` by `Invoke-SodCheck`) is only ever populated by the CSV path (`Update-SodMatrixes.ps1` synthesizes `"Must not combine 'X' with 'Y'"`). The DMF converter emits `source`/`target`/`severity` only — the richer, D365-native `RISK`/`MITIGATION` free text is dropped on the floor even though it's exactly what `description` is for.
- **No diff before publish.** The CSV path computes an explicit Added/Removed/Changed/Unchanged report + JSON changeset before writing anything; the DMF path only returns aggregate conversion stats (converted/skipped/unmapped counts) with no before/after comparison against the currently-live matrix.
