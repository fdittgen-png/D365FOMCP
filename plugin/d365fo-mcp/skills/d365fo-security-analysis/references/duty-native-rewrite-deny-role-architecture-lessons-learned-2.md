# Duty-native rewrite + Deny-role architecture — Lessons Learned (2026-07-09/10 sessions)

_Reference for the `d365fo-security-analysis` skill. Read on demand._


The bucket vocabulary described above was fully retired on 2026-07-09: SoD rules and role→duty grant/deny links are now keyed directly on the raw D365 AOT duty identifier (or a GUID for custom TBG-authored duties), matched by plain string equality. No bucket-collapse, no `DutyMapping.xml`. This closed the whole class of "hand-maintained mapping rots silently" bugs above by construction — there's no mapping left to rot.

### Deny roles are commonly a SEPARATE duty, not a Deny flag on the SAME duty
The single most important architecture finding from this rewrite: when auditing whether a Deny-type role actually mitigates a specific SoD conflict, **don't assume the Deny is recorded against the same duty ID as the one being conflicted.** Verified against real D365 config (TBG's "Deny vendor invoices" role): D365 orgs commonly build a mitigating control as an entirely separate, purpose-made **custom Duty** (often literally the same name as the role, e.g. Role "Deny vendor invoices" → Duty "Deny vendor invoices") whose own Privileges explicitly set access levels to Deny on specific entry points (e.g. `VendInvoiceInfoListPage`: Read/Update/Create/Delete = Deny). That custom duty's AOT ID has **nothing to do with** the standard Microsoft duty ID being conflicted (e.g. `VENDINVOICEVENDORINVOICESMAINTAIN` "Maintain vendor invoices"). Two different duty IDs, deliberately overlapping only at the entry-point level.

**Consequence for any SoD tool**: an exact duty-ID-equality check between "the conflicting duty" and "what this Deny role denies" will systematically and silently miss this — the most common real-world mitigation pattern — no matter how completely you capture duty-level Grant/Deny data. Duty-level matching is the wrong granularity for this pattern by construction, not due to a data-completeness bug.

**To detect it precisely** requires descending to Privilege/entry-point level: resolve both the granting duty and the Deny duty down to `{entry point, access type}` pairs (this is exactly what an AOT-enrichment side-file — duty→privilege→entry-point+access-level — is for) and intersect. Where the same entry point appears as Grant on one side and Deny on the other (ideally same access type — Update/Create/Delete, not just Read), that's a provable, quantifiable mitigation you can describe precisely ("Update access to VendInvoiceInfoListPage, granted by Duty A, denied by Duty B's Privilege C").

**When that's too much data/complexity to build** (a real, valid engineering tradeoff — it needs privilege-level export data for every Deny-type role in every checked hierarchy, which can be a lot of DMF surface area to ingest and keep current): a defensible fallback is a **coarse, name-based advisory signal** instead of a false-precision duty-level flag. Surface every Deny-type role present anywhere in the checked role's expanded hierarchy (id + name) alongside every violation, without asserting it mitigates any specific one — Deny roles are conventionally named after what they deny, so a human auditor can judge relevance from the name faster than the tool can prove it. Derive the "is this role Deny-type" signal from **two unioned sources**: (a) the Role's own type/flag attribute (catches a Deny role whose custom duty isn't referenced by any currently-active rule, so it has zero recorded duty-grant data at all — a real, verified case), and (b) any Deny-type duty-grant record for that role (catches a role that denies only some of its duties without being globally flagged Deny). Relying on only one of the two misses real cases.

**Why this beats "check the parent role hierarchy"**: walking role-hierarchy references (Parent roles / Sub roles) only proves *structural proximity* — that a Duty or Privilege sits somewhere in the same composite role as the conflicting grant. It cannot distinguish "this Deny genuinely covers the conflicting access" from "this Deny denies something in a totally unrelated module and just happens to be a sibling sub-role." Hierarchy position is a necessary precondition to check at all, never sufficient to *qualify* what's mitigated.

### Validate against D365's own native SoD-rule-validation infolog, not just internal consistency
D365 F&O has its own native SoD-rule validation that surfaces infolog messages per violating role (`Role "X" is in violation of segregation of duties rule "Y": The role contains duties "A" and "B".`). When building or auditing a duty-native SoD engine, get this real infolog output for at least one composite/profile role as independent ground truth and diff it against the engine's own output for the same role — an exact match (duty pair for duty pair) is much stronger validation than "the numbers look internally consistent" or "matches an old auditor spreadsheet," because it's checked against the same source D365 itself uses to flag the conflict. A prior/legacy reference dataset that *doesn't* match may simply be from a different, older rule source (e.g. a retired bucket-based matrix with broader or stale coverage) — don't assume the new engine is wrong just because it disagrees with an older reference; compare against the live D365 infolog first.

### Full-replace rule publish is a queryable-immediately-but-not-retroactive-to-existing-runs constraint
When the live SoD rule set (`SodRuleSet`) is stored as an overlay published independently of analysis runs, and the analysis engine bakes the ruleset into each run's merged model snapshot at merge time (rather than reading the rule store live at query time), **publishing new/corrected rules does not retroactively fix an already-completed analysis run.** The already-computed merged model still has the old ruleset (and its derived grant/deny links) baked in. Any workflow that "fixes the rules, then expects the existing dashboard/report to update" needs an explicit re-run step called out — this is easy to miss because the rule-publish endpoint returns a success response with no indication that downstream consumers are unaffected until the next analysis run.
